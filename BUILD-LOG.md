# Build log

A running record of how this project was built, including where APIMatic's
PayPal Context Plugin was used and — just as importantly — where it was not.
Kept live during the build rather than reconstructed afterwards.

Timestamps are Asia/Karachi.

---

## 2026-11-11 02:31 — Project scaffolded

Empty repo, directory structure, MIT license. No code yet.

Toolchain: Node v25.5.0, npm 11.8.0, git 2.50.1.

## 2026-11-11 02:3x — Scam script taxonomy (no plugin involvement)

Wrote `src/scripts/` — the taxonomy of scam scripts, their stages, and the
signals characteristic of each stage. This is domain modelling, not PayPal
integration, so the context plugin has no bearing on it. Recording that
explicitly because the boundary matters for the APIMatic write-up.

## 2026-11-11 03:0x — Offline engine passing 6/6

Wrote `src/engine/features.ts` (deterministic extraction), `offline.ts` (scorer),
`index.ts` (orchestrator), `cli.ts`.

Two real bugs found by running against fixtures rather than by reading code:

1. **Normalisation bias.** `scoreScript` divided matched signal weight by the
   script's own total possible weight. That systematically favoured scripts with
   few stages — the 3-stage "prize" script hit a perfect ratio on two signals and
   beat the 5-stage "romance" script that matched far more evidence. Romance and
   pig-butchering both misclassified as "prize". Fixed by ranking on absolute
   matched mass weighted by inverse document frequency across the script corpus,
   with no per-script normalisation.

2. **Scripts sharing a vocabulary could not be separated.** Grandparent and
   romance share secrecy, urgency, relationship-claim and isolation signals, and
   tied exactly on the early fixture. Added a temporal prior — the grandparent
   script runs in hours, romance takes months — which separates them cleanly.

Result: 6/6 on script identification and stage, including both controls staying
silent. `legit_large` (a $4,200 payment to an 11-day-old payee, the largest in
two years) scores 5 against a threshold of 20 and says nothing, which is the
behaviour the whole design is for.

Known weakness, recorded rather than tuned away: pig-butchering lands at
confidence 0.42 / tier 1 despite $18,000 already lost, because the offline
lexical matcher only recovers 5 of the signals in that narrative. That is the
gap the model path exists to close, and it will be shown as a direct comparison
rather than hidden.

No APIMatic involvement in any of the above — no PayPal API surface touched yet.

## 2026-11-11 03:5x — PayPal integration

Installed `@paypal/paypal-server-sdk@2.5.0` — the exact version the APIMatic
PayPal context plugin pins. Confirmed from the SDK's own type definitions that
it exposes Orders, Payments, Subscriptions, TransactionSearch and Vault
controllers and nothing else: no Payouts, Invoicing or Disputes. That matches
the plugin's documented coverage exactly, and it is why this project is built
on Transaction Search + Vault + Subscriptions rather than on Payouts.

Worth recording for the APIMatic write-up: the PayPal Server SDK is *itself*
generated by APIMatic — its source headers say so. That is why a context plugin
can describe the SDK's exact client shape, controller naming and error types
rather than inferring them from the REST documentation.

Two ingestion paths, kept deliberately separate:
- Transaction Search builds the 24-month behavioural baseline. PayPal documents
  a reporting lag of up to three hours, so it can never be the trigger.
- Webhooks are the trigger. An assessment that arrives three hours after the
  money left is not an intervention, it is a receipt.

Added `verify-adapter.ts`: renders each fixture into PayPal's exact wire shape,
reads it back through the production adapter, and asserts the assessment is
unchanged. Runs with no credentials, so a reviewer can execute it on a clean
checkout. 6/6 — 921 transactions and 47 payees round-trip with no identity
fragmentation and no classification drift.

That test exists for one specific failure: PayPal's `account_id` is absent on
many card and guest flows, so payee identity falls back to email and then to
display name. Get that wrong and a single recipient fragments into several,
which silently destroys the escalation and reciprocity signals — both are
computed per payee. The test deliberately strips `account_id` from half the
payees to exercise the fallback chain.

### APIMatic context plugin — install blocked in this environment

`npx context-plugins install https://github.com/paypaldev/server-sdk-context-plugin-preview`
was refused by the sandbox running this build, because it executes code fetched
from a remote URL. Recorded here rather than worked around. Needs to be run by
hand before submission, and this log updated with what the plugin actually
changed about the PayPal code written afterwards.

## 2026-11-11 04:4x — Server, console, and a finding I am not tuning away

Two-pane demo: the person's screen and the trusted contact's console side by
side, so one event is visible landing in both places at once.

Chart decisions, against the data-viz method rather than taste:
- Discrete payment events at irregular intervals, so bars anchored to a
  baseline. A connected line would imply the amount existed between events.
- Inbound money is a ring, not a fill. Shape carries the distinction because
  the blue/aqua pair measures tritan ΔE 4.0 in dark mode — low enough that hue
  alone is not safe. Both modes otherwise pass the validator (adjacent CVD ΔE
  23.1 light / 19.6 dark against a ≥8 target).
- Aqua sits at 2.74:1 on the light surface, below the 3:1 floor. The relief rule
  applies and is satisfied twice over: the inbound point is always directly
  labelled, and the AG Grid evidence table is a full table view of the same data.
- Status colours (tier) never travel alone — every tier ships an icon and a label.

Caught by screenshotting rather than by reading the code: the control fixture
has 50 routine payments to a grocery delivery service, and the first version
drew and labelled every one of them. Unreadable. Now capped to the most recent
12 with the caption saying so, selective direct labels (pending, inbound, and
the peak), and thinned date ticks.

Also caught visually: the evidence grid was sorting secrecy (weight 10) to the
bottom. Secrecy and isolation are the signals that separate fraud from an
ordinary private payment, so they now sort first.

### Finding: a webhook alone is not enough, and that is correct

Posting a single realistic webhook — $2,400, brand-new payee, memo "urgent bail
for Tommy, please do not tell mom" — scores 19 against a reporting threshold of
20, and the system stays silent.

I am recording this rather than lowering the threshold. It is the honest
result and it says something real about the architecture: the payment event by
itself does not carry enough narrative. Four signals fire from a memo; twelve
fire once the conversation history is present. The companion-app context is
load-bearing, not decorative, and a version of this that only watched payment
events would be much weaker than the demo suggests.

## 2026-11-11 (later) — APIMatic context plugin, installed and actually used

The official installer (`npx context-plugins install <github url>`) executes code
fetched from a remote URL and was refused by the sandbox. Rather than work around
that: cloned the repo, inspected it (61 files, all Markdown, no executable code),
and copied the TypeScript skill set to the project-scope `.claude/skills/`
location, with attribution in `.claude/skills/ATTRIBUTION.md`. The global plugin
registry was left alone — it is managed state with a hashed index, and
hand-editing it risks corrupting the user's config.

Then used it, which is the part that counts. Three concrete changes, written up
in full in `evidence/plugin/findings.md`:

1. **Error payload casing.** Error payloads keep wire names — `debug_id`, not
   `debugId` — unlike every model in the SDK. From memory this code would have
   read `undefined` on every error path.
2. **Which error classes Transaction Search throws.** `DefaultError` on
   400/403/500, `SearchError` otherwise, confirmed by reading the controller
   body as the skill instructs rather than guessing from the operation name.
3. **A real bug: RESULTSET_TOO_LARGE.** `SearchError` carries `total_items` /
   `maximum_items` for exactly this case. The first `fetchHistory` treated every
   error the same and broke out of the window, which would have silently dropped
   a whole month from the 24-month baseline. Since every behavioural ratio in
   this project is measured against that baseline, the failure would have been
   invisible and would have biased the system toward under-reacting. Now bisects
   the window and recurses.

Boundary, stated plainly: the plugin informed PayPal SDK usage only. It had no
bearing on the taxonomy, the feature extractor, the scorer, the model prompt or
the console.

## 2026-11-11 (later) — Webhook signature verification

Closed the largest named gap. `src/paypal/verify-webhook.ts` calls PayPal's
`/v1/notifications/verify-webhook-signature`, with the OAuth token coming from
the SDK's `OAuthAuthorizationController` so there is exactly one credential path.
The SDK ships no webhooks controller, so that endpoint is called directly.

Two details that are easy to get wrong and would both fail silently:

- Verification is computed over the **raw request bytes**. Re-serialising
  `req.body` changes key order and whitespace and the signature will not match,
  so the server captures the raw buffer in `express.json({ verify })` before
  parsing.
- It **fails closed**. An error while verifying returns 503, not success. An
  exception during a security check is not permission to proceed.

Without credentials the endpoint still runs so the demo works on a clean
checkout, but it reports `signatureVerified: false` on every response and
`/api/health` says `DISABLED` with the variables needed. Visible rather than
silent: a reviewer should see this property, not discover it.

Also fixed a self-inflicted testing error worth recording: an earlier `pkill`
pattern did not match the running server, so a stale process kept serving old
code on port 3000 and the new fields appeared to be missing. Killed by port
instead. The lesson is that the first result looked like a code bug and was an
environment bug — worth a second look before changing code that is already correct.


## 2026-11-12/13 — Model provider swap, then the bugs that only run-time finds

Moved the model path from Anthropic to Groq (`openai/gpt-oss-120b`, reasoning
effort high). The Anthropic-specific bindings have no Groq equivalent, so they
were replaced rather than adapted: `messages.parse` + `zodOutputFormat` became
`chat.completions.create` with a strict `json_schema` response format generated
from the same zod schema that validates the reply, so the schema stays the one
source of truth. The explicit `cache_control` block is gone — Groq has no
equivalent — so the taxonomy simply leads the system message for automatic
prefix caching.

Two defects the swap exposed immediately, both of which had been invisible
while the model path had never actually run:

- `SECOND_THOUGHT_MODEL ?? default` left the model name empty, because
  `.env.example` ships the override present and blank. Groq answered
  `model_not_found`. `??` only catches null and undefined; `''` is neither.
- groq-sdk's 60s default timeout is short for high reasoning effort over the
  taxonomy prompt. One fixture timed out and fell back to the offline scorer
  with no visible failure — the only trace was the `uncertainty` string.

### The model path, executed for the first time

6/6 on script identification, both controls silent. Then two findings that are
only visible once there is a second engine to compare against:

**Confidence is not calibrated and must not drive the tier.** The model returns
0.92–0.96 on essentially everything it flags, including both `none` controls.
`chooseTier` read confidence, so every true positive collapsed onto the top two
rungs and the five-rung ladder the design rests on went flat. The offline
scorer never showed this because it *derives* confidence from evidence mass and
separation, so the two quantities agreed. Tier now comes from observed signal
mass, which both engines compute identically from the shared vocabulary.
Confidence is kept as a ceiling only: it can hold a shaky assessment back, it
can no longer push a thin one up.

**19 of 24 stages were unreachable.** A stage counted as "reached" only when
one of its signals weighed >= 8, and only four of the sixteen signal kinds do.
So the stage pinned to wherever secrecy or isolation sat, and no later stage
could ever be reported however much evidence there was for it. That is the one
error this system cannot afford: the stage chooses the prediction shown to the
person, and predicting a move they have already watched arrive is worse than
saying nothing. A stage is now also reached proportionally, against its own
vocabulary rather than a global cutoff.

Both engines then agreed that `grandparent_early` is stage 4, not the stage 3
in its ground truth. The taxonomy defines stage 4 as "a first payment has been
requested or sent" and the payment is sitting pending, so the fixture was
wrong — its intent, caught before any money moves, is unchanged. The prediction
it shows changed from one the person has already seen to the next larger
request and the instruction not to involve their bank.

### Rate limits are a demo risk

Five consecutive runs of the six fixtures: runs 3, 4 and 5 came back entirely
offline. The Groq free tier's quota was exhausted partway through run 2 and the
fallback is silent by design. The console badges the engine actually used, so
it is visible there, but `/api/health` reports "llm available" from the mere
presence of a key, which can be wrong. Worth knowing before a live demo: the
system degrades to the weaker engine rather than failing, which is the right
behaviour and the easiest thing to miss.

### Two silent bugs in the PayPal path, found by writing its first test

Neither could have been found by the live sandbox testing this project cannot
do — an account with no transaction history exercises no windowing, no paging
and no error branch. Both are in the commit message for `verify-ingest.ts`; in
short: the SDK returns its own camelCase model rather than PayPal's JSON, and
`err.result` is never populated for an operation that registers no `throwOn`
statuses, which had silently disabled the `RESULTSET_TOO_LARGE` bisect
altogether. `evidence/plugin/findings.md` has been corrected, including the
part where our own grep spanned two operations and we recorded the union.

### Variance: measured, and mostly blocked by the quota

Five runs of the six fixtures, on the corrected code. Only **14 of 30**
assessments reached the model — the Groq free-tier quota ran out partway
through, exactly as it had the first time. Of the 14 that ran: script correct
14/14, stage matching 14/14, both controls returning `none` every time they
were assessed by the model.

What that does not establish is stability. An earlier run under the same prompt
returned stage 5 for `pig_butchering` where these three returned 6, so the
model's stage output does vary between runs. Confidence stayed in 0.90–0.97 on
every fixture including the controls, which is the clearest confirmation that
it is not a calibrated quantity and was never safe to compute the tier from.

Tier, now that it comes from evidence mass, was identical across every model
run of the same fixture. That is the property that was wanted: the ladder is
reproducible even where the model's own numbers are not.

The README reports 14 assessments rather than "6/6", because 6/6 from a single
run of self-written fixtures is not a result worth defending.
